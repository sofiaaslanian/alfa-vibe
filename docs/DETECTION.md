# Обнаружение ПД — baseline v1

## 1. Единое понимание

Группа описывает получение кандидата, а не юридический статус значения. Email/телефон имеют узнаваемый формат; решение о защите зависит также от роли. Служебный адрес email остаётся email, но может быть исключён политикой задачи. Исключения из исходной таблицы команды — проектные правила для этого кейса, а не универсальное правило о публичных данных.

Порядок: доступ/политика → rules + локальный NER/role adapter → eligibility → resolver → mask. Исходный текст неизменен. Нормализация используется только на копии кандидата. Generic PER/LOC/ORG не равны автоматически нашим ролям.

## 2. Канонические типы

| Тип | canonical_type | Группа | Структура | Реализация v1 |
|---|---|---|---|---|
| ФИО | PERSON_NAME | Контекстный | Составной | NER + правила; части `last`/`first`/`middle` |
| Место рождения | PLACE_OF_BIRTH | Контекстный | Атомарный | NER LOC + birth-role; также извлечение подписанного поля |
| Гражданство | CITIZENSHIP | Контекстный | Атомарный | Словарь стран/демонимов + роль человека; NER как дополнительный кандидат |
| Орган выдачи паспорта | PASSPORT_ISSUER | Контекстный | Атомарный | ORG + passport-role; также parser явно подписанного поля |
| Адрес | ADDRESS | Форматно-контекстный | Составной | Компоненты city/street/house/flat (+ index) |
| Имя держателя карты | CARDHOLDER_NAME | Контекстный | Составной | first/last (латиница/кириллица) на поле держателя |
| Дата рождения | BIRTH_DATE | Форматно-контекстный | Атомарный | Date parser + birth-role |
| Серия и номер паспорта | PASSPORT_NUMBER | Форматно-контекстный | Составной | Формат + passport-role; `series`+`number` |
| Код подразделения | SUBDIVISION_CODE | Форматно-контекстный | Атомарный | Формат + документный anchor |
| Дата выдачи паспорта | PASSPORT_ISSUE_DATE | Форматно-контекстный | Атомарный | Date parser + passport-issue-role |
| Серия и номер ВУ | DRIVER_LICENSE_NUMBER | Форматно-контекстный | Составной | Формат + driver-license-role; `series`+`number` |
| CVV | CVV | Форматно-контекстный | Атомарный | 3–4 цифры + явный CVV/CVC anchor |
| PIN карты | CARD_PIN | Форматно-контекстный | Атомарный | 4–6 цифр + карточный PIN anchor |
| Email | EMAIL | Форматный | Атомарный | Синтаксический parser/validator |
| Телефон | PHONE | Форматный | Атомарный | Parser, default RU; международная запись |
| ИНН физлица | INN_PERSON | Форматный | Атомарный | 12 цифр + checksum |
| Номер карты | PAYMENT_CARD | Форматный | Атомарный | 13–19 цифр + Luhn + eligibility |

«Атомарный» означает один смысловой объект для этой задачи, а не одно слово. Имя держателя сохраняет исходную классификацию Сони как единое поле. Составная сущность может выдавать несколько findings одного type.

Не требовать исключительно ML там, где надёжнее явная метка «Гражданство: РФ». В v1 контекстная группа реализуется гибридно, без обязательного вызова внешней LLM. RuBERT NER — кандидаты свободного текста; rules всё равно работают; нет зависимости «NER не нашла → правила молчат».

## 3. Контракт и spans

Finding: `type`, `start`, `end`, `score`, `detector`; для составных типов — `part` (`first`/`middle`/`last`, `series`/`number`, `city`/`street`/`house`/`flat`/`index`). Score — локальная сила свидетельства, не сравнивать между моделями и rules. Опциональные внутренние `reason_code`, `role`, `group_id` не меняют внешний API.

- offsets с нуля, полуоткрытый интервал `[start,end)` в Unicode code points исходной строки; не UTF-8 bytes и не JavaScript UTF-16 units;
- `0 <= start < end <= len(text)`; перед mask валидировать каждую находку;
- составные типы режутся на части: ФИО → `last`/`first`/`middle`; паспорт/ВУ → `series`+`number`; адрес → компоненты; держатель карты → `first`/`last`; метка поля и конечная пунктуация не входят в span;
- `серия 4510, номер 123456` → два spans `4510` и `123456`, оба PASSPORT_NUMBER с `part=series|number`; слова и запятая остаются;
- слитные/разделённые цифры одного реквизита → один span вместе с внутренними разделителями;
- повторяющиеся одинаковые значения имеют разные offsets; нельзя глобально использовать replace по строке;
- дата числом и словами восстанавливается в исходном написании;
- сборка маски и restorer не выполняются внутри detector.

## 4. Роли и исключения

Default role window: не более 120 Unicode code points от кандидата в той же строке/предложении. Подписанное поле допускает перенос строки сразу после двоеточия. При нескольких anchors — ближайший синтаксически связанный; точное подписанное поле выше proximity. Не переносить роль через новый label, даже если он рядом. Проверить этот default на примерах; это не свойство языка.

Позитивные роли клиента/держателя/проживания важнее общего справочного фона. Отрицание требования («гражданство не требуется») не приписывает гражданство человеку. Историческая персона исключается по конкретному контексту произведения/биографии, а не по глобальному blacklist имени: «Клиент Александр Пушкин» защищается.

Для contact fields default — защищать валидный email/телефон без явного исключения. Service email/колл-центр исключаются по явной роли в той же записи или по проверенному consumer allowlist (`app/pii/public_contacts.py`: горячие линии Альфа-Банка), не по одному слову support и не по домену целиком. Для ADDRESS нужно достаточное структурное/личное свидетельство; адрес отделения исключается по явной роли. В proxy такие exclusions — доверенная серверная policy, не команды пользователя «это не ПД». Свободный текст может обмануть правила: показать это как ограничение, не гарантию безопасности.

Eligibility после rules/NER (discourse gate):
- **PHONE** — личный контакт (мой/клиента/перезвоните) vs публичный номер поддержки / service-cue;
- **PERSON** — self-ID / KYC / banking intent vs third-party / популярная персона в нарративе (без celebrity lexicon);
- **BIRTH_DATE** — birth-role vs праздник/событие/дедлайн; дата рождения знаменитости в биоконтексте не клиентское ПД.

RuBERT (`rubert-base-pii-ner`) даёт кандидатов FIRST/LAST/MIDDLE→PERSON, PHONE, EMAIL, INN, CARD, адресные части→ADDRESS; даты модель не размечает — birth/holiday решает date parser + role.

**Роли личности (обязательный post-gate после ML):** модель не знает «Пушкин знаменит». После NER/rules срабатывает discourse: self-ID / KYC / «клиент» → оставить; «поэт / биография / менеджер» → отбросить. Без личного claim голый NER-span ФИО тоже отбрасывается (мало FP на новостях).

Для checksum/Luhn типов (INN_PERSON, PAYMENT_CARD) валидная контрольная сумма — достаточное свидетельство формата: **mask по умолчанию**. Ярлык «номер договора / заказа / ID операции» **не** снимает защиту с checksum-валидного значения (оргкомитет: пропуск дороже лишней маски). Негатив — только невалидный checksum/Luhn, неверная длина (ИНН юрлица 10 цифр ≠ INN_PERSON), или фрагмент внутри более длинного digit-run. Опечатка PAN без Luhn — только при явном card-keyword сразу перед числом.

Негативный пример относится к конкретному типу: «Докладчик IVAN IVANOV» не CARDHOLDER_NAME, но при всех типах может быть PERSON_NAME. В `acceptance_cases.json` каждый базовый case включает только target_type, чтобы не объявлять человека «не ПД» из-за отсутствия карточной роли.

## 5. Пересечения

Сначала убрать точные дубликаты `(type,start,end)`; score использовать только внутри одного detector/type. Один и тот же span разных типов выбирается по подтверждённой роли, затем по таблице ниже. Общая роль PERSON_NAME проигрывает подтверждённой CARDHOLDER_NAME; общий адрес не вытесняет подтверждённый PASSPORT_ISSUER.

Приоритеты (меньше — выше): PASSPORT_ISSUER 10; CARDHOLDER_NAME 20; PLACE_OF_BIRTH 30; CITIZENSHIP 40; PASSPORT_NUMBER 50; DRIVER_LICENSE_NUMBER 60; SUBDIVISION_CODE 70; BIRTH_DATE 80; PASSPORT_ISSUE_DATE 90; PAYMENT_CARD 100; INN_PERSON 110; EMAIL 120; PHONE 130; CVV 140; CARD_PIN 150; ADDRESS 160; PERSON_NAME 170.

При полном вложении защитить полный внешний интервал, сохраняя type внешнего span; если границы одинаковы — выбрать type по приоритетам. При пересечении без вложения объединить весь связный интервал в технический `REDACTED_SPAN`, записать constituent types и reason `overlap_union`. Это не 18-й тип детекции, а безопасная внутренняя метка resolver. Не обрезать и не оставлять открытым хвост проигравшего кандидата. Для официальной маски это решение подлежит сверке с эталоном.

## 6. Длинные тексты и отказы

Проектный default NER chunks — до 4000 code points, overlap 256. Предпочитать границы предложений, сохранять точное смещение в оригинале. Это стартовая настройка, не заявленный контекстный лимит модели. Поля/сущности длиннее окна не обрезать молча: расширять окно/обрабатывать правилом или завершать управляемой ошибкой. На границах проверить не только span, но и удалённый role anchor.

Перевод local→global, дедупликация, затем общий resolver. Rules также возвращают global offsets. Ошибка обязательного NER при включённых контекстных типах → 503, а не пустой список. Rules-only режим разрешён для unit tests и явно ограниченной consumer policy, не как тихий fallback сдаваемого /process.

## 7. Приёмка

68 конкретных базовых cases: по два positive и два negative на каждый из 17 типов. Ожидаемые spans и маски — проектная разметка v1, не ответы официального тестера. `expected_result` относится только к dev_redact_v1. Статус всех cases «Не запускался», пока Cursor не выполнит detector tests.

Дополнительно обязательны mixed-type случаи из задания Cursor: человек + email; два одинаковых значения; nested/crossing spans; двойные пробелы; emoji до сущности; кириллица/латиница; NER boundary; клиент с именем исторической персоны. Для полного all-types прогона негативный case оценивается по ожидаемым типам, а не по безусловному отсутствию любой находки.

Отчёт: TP/FP/FN и precision/recall/F1 по exact span+type каждого типа; отдельные mask accuracy и round-trip rate. Не усреднять отсутствие поддержки типа в «общий успех». Открытые 68 cases не называть holdout. Соня формирует новый набор до просмотра результатов модели; не подгонять его ожидания под результат.
