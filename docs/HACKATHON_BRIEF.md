## Проблематика

Сегодня все команды, работающие с LLM в Банке, сталкиваются с необходимостью защищать персональные данные, однако каждая команда решает эту задачу самостоятельно. Это создаёт системные проблемы:

- текущие решения разработаны разными командами под свои требования и ограничения;
- решения недостаточно гибкие по настройке маскирования для разных типов ПД;
- демаскирование присутствует лишь частично;
- сервисы должны быть отказоустойчивыми и держать большую нагрузку.

Итог: разрозненные решения трудно переиспользовать, команды тратят лишние ресурсы на своё решение.

Трек для: LLM/AI, backend/frontend, UX, PM/аналитик, DS/ML, ИБ/банковские процессы.

**Задача команды:** создать приложение, которое **качественно и быстро** обрабатывает:
1. запрос системы-потребителя в LLM;
2. ответ, который формирует LLM.

В обработке: **идентификация ПД → маскирование → демаскирование**.

### Что важно увидеть жюри / заказчику

- насколько хорошо сервис находит данные, которые нельзя передавать без обработки;
- насколько мало **ложных срабатываний**;
- сохраняется ли после обработки **смысл запроса для AI-модели**;
- можно ли **управлять правилами** для разных систем;
- насколько просто **подключить нового потребителя**;
- что происходит при **ошибках или недоступности** отдельных компонентов;
- не попадают ли исходные защищаемые данные в **логи и технические метрики**.

Архитектура должна позволять **добавлять новые правила и сценарии без переделки всего сервиса**.

## Образ решения / ключевые требования

Модуль безопасности (демо-прокси) в цепочке:

`система-потребитель → модуль (ID/MASK) → LLM → модуль (UNMASK) → потребитель`

- легко встраивается в цепочку «система-потребитель — LLM»;
- обязательное покрытие описанных типов ПД;
- строго: **никаких утечек**, шифрование, минимизация данных;
- недопустимость критичных ошибок + уровень качества обработки;
- SLA: скорость, доступность, стабильность;
- соответствие законодательству РФ, нормативной базе и требованиям ЦБ.

## Задача

### 1. Основные / ключевые требования

| Требование | Детали |
|------------|--------|
| Функционал | **Идентификация → Маскирование → Демаскирование** (запрос и ответ LLM) |
| Качество | Точность **≥ 95%** |
| Мульти-тенантность | Несколько систем-потребителей с индивидуальными настройками |
| Allowlist систем | Ограниченный список систем, имеющих право обращаться в сервис |
| Логирование | Подробное на каждом этапе; в тесте — типы ПД **по каждому запросу** |
| Метрики | **Latency**, **RPS**, **TPS** (tokens per second) |
| Контекст | Массивы до **100 000 токенов** |
| Latency | **≤ 1 сек** |
| RPS | **≥ 1000** (бонус: 2000) |
| Расширяемость | Новые типы ПД и правила — без переписывания ядра |

### 2. Функциональные требования

#### 2.1 Идентификация типов ПД

Обязательные типы: ФИО; дата/место рождения; серия и номер паспорта; гражданство; орган, выдавший паспорт; код подразделения; дата выдачи паспорта; серия и номер водительского удостоверения; адрес (страна, индекс, город, улица, дом, квартира и т.п.); email; телефон; ИНН; номер карты; CVV; пин-код карты; имя держателя карты.

Дополнительно по идентификации:

- механизм «это именно ПД»: упоминание поэта **Александра Пушкина** ≠ ПД; **адрес отделения Банка** ≠ клиентские ПД;
- возможность **расширения** списка типов;
- идентификация **не зависит от регистра**;
- логирование выявленных типов ПД в тесте по каждому запросу.

#### 2.2 Маскирование

Учитывать вариации написания, в т.ч.:

- регистр;
- разный порядок даты (мм.дд.гггг, гггг.дд.мм и т.п.);
- дата **текстом**, не только числами;
- разделяющие слова («серия хххх номер хххххх» и т.п.).

#### 2.3 Демаскирование

Преобразование замаскированного текста в незамаскированный **с сохранением местоположения знаков**.

Оценка на платформе: не только exact match — **по степени похожести**; на вход demask подают уже замаскированную строку, сравнивают с исходником.

#### 2.4 Общие функциональные требования

- подробное логирование на каждом этапе;
- метрики Latency / RPS / TPS;
- ограниченный список систем с доступом к сервису;
- гибкая настройка:
  - список систем (вкл/откл обращения в модуль);
  - перечень типов ПД для ID/маскирования **по системе**;
  - наличие демаскирования **по системе**;
  - краткая инструкция по настройке (**не более 5 предложений**);
- качество ID/mask/unmask **≥ 95%**;
- крупные тексты до **100 000 токенов**.

### 3. Нефункциональные требования

- **Безопасность:** обработка в защищённом контуре, внутренние стандарты ИБ банка; исходные ПД не в логах/метриках.
- **Надёжность:** корректная обработка ошибок API; **деградация** при недоступности сервисов; понятные сообщения пользователю.
- **Производительность:** в ТЗ Latency ≤ 1 с, RPS ≥ 1000; **для баллов жюри целимся Latency ≤ 0.5 с** при RPS 1000 (см. критерий 3.5).
- **Масштабируемость:** новые типы ПД и рост RPS при сохранении Latency (репликация, очереди, балансировка — см. ниже).

### Хостинг

### Языки входного текста

## Автоматическая проверка решений (обязательно)

**Обе проверки обязательны.** Решение, не прошедшее автоматическую проверку качества кода, а также не развёрнутое для нагрузочного тестирования, **не будет учтено**.

### 7.1 Автопроверка качества кода

- Решение загружается **архивом `.zip`**; проверка стартует автоматически после загрузки.
- В архив кладём **только исходный код**.
- **Не включать:**
  - большие файлы: датасеты, дампы БД, архивы, медиа, скомпилированные бинарники;
  - зависимости и окружения: `node_modules`, `.venv`, `venv`, `env`, `.env` и т.п.;
  - артефакты сборки: `target`, `build`, `dist`, `out`, `bin`, `obj`;
  - служебное: `.git`, `.idea`, `__pycache__`, `coverage`.
- Архив должен быть разумного размера; код — в корне или в понятной структуре.
- Чем чище и легче zip — тем быстрее и надёжнее проверка (зависимости система не ждёт: смотрит исходники).

**Как смотрят код (автопроверка качества):** оценка на базе **SonarQube**. Учитываются **значащие строки** (не «весь код» целиком: мусор/простыни не в фокусе — читают смыслово значимое).

### 7.2 Нагрузочное тестирование

- Решение нужно **развернуть** (доступно по URL на время прогона).
- Обязательный API-контракт: **`POST /process`** — полностью в **Приложении A** ниже.
- Нагрузка идёт по эталонному датасету; оценивают:
  1. точность маскирования;
  2. точность демаскирования (по **степени похожести** с исходником, не только exact match);
  3. поведение под нагрузкой.
- Контракт — **Приложение А**; инструкция по прохождению проверки — **Приложение Б**.
- Нужно реализовать контракт и держать сервис доступным по указанному URL во время теста.

## Приложение A — контракт API `POST /process`

Единый контракт для всех команд. Система проверки (**AlfaSonar**) бьёт в него на нагрузочном тесте.

### Запрос / ответ

```http
POST /process
Content-Type: application/json
```

```json
{ "payload": "<строка>", "payload_id": "<идентификатор>" }
```

→ **200**

```json
{ "result": "<строка>" }
```

### Логика (обязательно)

- Эндпоинт **один** — и маскирование, и демаскирование.
- Направление по **`payload_id`** (ключ корреляции mask → demask).
- **Первый** запрос с новым `payload_id` → **маскирование** (`payload` = исходник) → вернуть маску и **запомнить** соответствие.
- **Второй** запрос с тем же `payload_id` → **демаскирование** (`payload` = ваша маска) → вернуть исходную строку.
- Ответ всегда: `{"result": "…"}`.
- Поля обязательны: `payload`, `payload_id` → `result`.

### Коды ответа

| Код | Смысл |
|-----|--------|
| 200 | успех |
| 429 | слишком много запросов — **допустимо** под нагрузкой; система ждёт/ретраит (`Retry-After`); если 429 не проходит — решение «не держит» нагрузку |
| 4xx | ошибка запроса |
| 5xx | внутренняя ошибка |

### Транспорт

- Можно **http** или **https** (self-signed ок: проверка с `ssl_verify=false`).

### Самопроверка формата

Эталон формата (не эталон качества масок):

```bash
curl -X POST https://process-test.holydev.space/process \
  -H "Content-Type: application/json" \
  -d '{"payload":"тестовая строка","payload_id":"selfcheck-1"}'
```

## Приложение B — нагрузочное тестирование

Условия одинаковы для всех команд. Датасет: категории ПД из ТЗ (ФИО, даты, паспорт, …, сложные предложения).

### Пошаговая логика

По каждому элементу — **пара** запросов с одним `payload_id`:

1. **Прямая (mask):** исходная строка + новый `payload_id` → ваша маска.  
   Сравнение с **эталонной маской**: метрика — **нормированное span-based расстояние Левенштейна** в диапазоне **[0..1]** (степень похожести, не только exact match).
2. **Обратная (demask):** система шлёт **вашу же маску** + тот же `payload_id` → вы возвращаете исходник.  
   Сравнение с исходной строкой из датасета (та же логика похожести).

### Надёжность (обязательно)

| Правило | Значение |
|---------|----------|
| Таймаут одного запроса | **10 сек** (дольше = неответ) |
| Ретраи | до **2** (итого до 3 попыток) → эндпоинт **идемпотентен** по `payload_id` |
| 429 | допустим; учитывается Retry-After. Если 429 на mask — demask по элементу не запрашивают; если на demask — учитывается, прогон идёт дальше |
| Стоп прогона | после **5 невалидных** запросов подряд (429 **не** сбрасывает и не считается невалидным; успешный ответ сбрасывает счётчик) |
| Нагрузка | ~**5 минут**, целевой **RPS 1000**, элементы переиспользуются |
| Latency | ориентир **≤ 1 с** (не жёсткий лимит прогона) |

### Чек-лист прохождения

- [ ] `POST /process` строго: `{payload, payload_id}` → `{result}`
- [ ] соответствие по `payload_id`; повторный запрос возвращает исходник
- [ ] стабильно под нагрузкой (RPS 1000+)
- [ ] идемпотентность + корректный 429 при перегрузке
- [ ] сервис доступен по URL (http/https) в момент прогона

**Автопроверка кода (zip):** отдельно; качество кода смотрят по исходникам (значимые строки / Sonar-класс инструментов). Точность mask/demask на load-тесте — **span-based Levenshtein**, не «весь файл целиком».

## Оценивание жюри (макс. 30 баллов)

Источник: критерии задачи «Модуль безопасности персональных данных» (AlfaGen).

### Общие принципы

- Оценивают **качество и скорость** модуля (ID → MASK → UNMASK), **гибкость настройки** и **качество демо**, а не объём кода.
- Production-готовность **не** оценивается: достаточно демо-прокси `система-потребитель → Модуль → LLM`.
- Свободная экспертная оценка в рамках диапазонов баллов.
- Проверка по датасету **17 категорий** (от ПД до данных карт).
- **Утечка** немаскированных ПДн в LLM-запрос/ответ на демо → существенное снижение по всем связанным критериям.

### Шкала (сумма ≤ 30)

| # | Критерий | Баллы |
|---|----------|-------|
| 1 | Качество идентификации и маскирования ПДн | 0–6 |
| 2 | Корректность демаскирования | 0–3 |
| 3 | Точность отнесения к ПДн и устойчивость к вариациям | 0–4 |
| 4 | Гибкая настройка и расширяемость | 0–4 |
| 5 | Производительность и SLA | 0–4 |
| 6 | Безопасность, логирование и метрики | 0–3 |
| 7 | Расширенные сценарии (доп. возможности) | 0–3 |
| 8 | Качество демо и презентации | 0–3 |

### 3.1 Качество ID и маскирования (0–6)

- Быстрый тест: **5–10 предложений** с ПДн → сверить с правилами маскирования.
- Основа балла — **полнота покрытия** типов из перечня.
- Маска делает текст **нечитаемым и невосстанавливаемым** без модуля.
- **Нет пропусков:** ПДн не уходят в LLM в открытом виде.
- Близкие к правилам вариации масок — балл не снимают; систематические пропуски целых типов — сильно режут.

### 3.2 Корректность демаскирования (0–3)

- Быстрый тест: взять маску из 3.1 → обратное преобразование.
- Совпадение с оригиналом, **позиции знаков сохранены**.
- Demask доступен **только** авторизованной/настроенной системе (см. 3.4).
- **Если demask нет → 0**, без компенсации другими критериями.
- Токенизация/детокенизация **засчитывается наравне** с классическим demask.

### 3.3 Точность отнесения к ПДн и вариации (0–4)

- Ловушки: **Пушкин**, **адрес отделения Банка** + иной регистр, формат даты (мм.дд.гггг, дата текстом), «серия … номер …».
- Ложные срабатывания отсутствуют или минимальны.
- Не зависит от регистра; вариации дат/слов распознаются.
- Свободная оценка «умности» эвристики/ML в диапазоне баллов.

### 3.4 Гибкая настройка и расширяемость (0–4)

- **Если нет README** с описанием настроек → критерий = **0**.
- Проверка через README: вкл/откл систем; типы ПДн и факт маскирования по системе; demask по системе.
- Расширение списка ПДн **без переписывания ядра** (конфиг / плагины / справочник).

### 3.5 Производительность и SLA (0–4)

- Быстрый тест: замер latency на 1–2 запросах (логи/метрики команды).
- **Целевой ориентир жюри:** Latency **≤ 0.5 с** при RPS 1000 (строже, чем «≤1 с» в общем ТЗ — целимся сюда).
- Честная оценка своего latency с метриками засчитывается даже без полного load-теста.
- Крупные тексты до **100 000 токенов** без падения.
- RPS **2000** при том же latency — повышенный уровень (можно учесть и в 3.7).
- Нет нагрузочного подтверждения → балл снижается, но **не обнуляется** при корректной архитектуре.

### 3.6 Безопасность, логирование и метрики (0–3)

- Показать лог одного запроса + экран/выдачу метрик.
- Логи типов ПДн по запросу; подробные этапы обработки.
- Метрики **Latency / RPS / TPS**.
- Ограничение круга систем (allowlist, ключи, mTLS — на уровне демо).
- Нет утечек ключей/реальных ПДн в артефактах сдачи; шифрование хранилища соответствий — на усмотрение жюри.
- Понятные ошибки; деградация при недоступности компонентов.

### 3.7 Расширенные сценарии (0–3)

Свободный критерий: **по 1 баллу** за уверенно показанное, **макс. 3**:

1. Токенизация/детокенизация или синтетика  
2. Вид маскирования/токенизации под систему  
3. RPS 2000 при Latency **≤ 0.5 с**  
4. Документы УЛ кроме паспорта РФ  
5. Контекстное маскирование (комбинации типов, настраиваемо)

### 3.8 Качество демо и презентации (0–3)

- Короткое объяснение принципа и архитектуры (**1–2 минуты**).
- Схема: `Система-потребитель → Модуль (ID → MASK → LLM → UNMASK) → Потребитель`.
- Ответы на вопросы: лаконично, аргументировано, корректно.

### Обязательные артефакты на сдачу (критерии)

1. Рабочий демо-сервис-прокси + README, точки входа к LLM и обратно.  
2. Инструкция для жюри: тестовый текст → mask/unmask → где логи и метрики.  
3. Схема архитектуры и настроек (системы, типы ПДн, правила).  
4. **Сведения о производительности** (замеры/нагрузочный тест) + список доп. возможностей.

**Стоп-сигнал:** если на живом демо **реальные ПД уходят во внешний LLM без маскирования** — это провал ключевой функции (независимо от прочих плюсов). Фиксируется отдельно как **утечка данных**.

### 1. Доверие: решение реально защищает данные?

Вопрос: *«Готов ли я поставить это между нашими внутренними системами и внешним LLM?»*

**Хорошие признаки**
- На демо во внешний LLM не уходят фрагменты ПД в открытом виде.
- Маскированный текст корректно восстанавливается без потери информации.
- Система не срабатывает на «ловушки» (напр. Пушкин / адрес офиса ≠ клиентские ПД).

**Тревожные признаки**
- Хотя бы одна утечка на демонстрации.
- Демаскирование неточное или ломается.
- Маскирует всё подряд и ломает смысл промпта для LLM.

### 2. Внедряемость: можно ли поставить в реальные системы?

Вопрос: *«Что мешает начать пилот с этой командой через месяц?»*

**Хорошие признаки**
- Скорость показана **цифрами и метриками**, не обещаниями.
- Маскирование включается/настраивается под разные системы-потребители **без правки кода**.
- Новые типы данных добавляются через настройки/справочник, а не правку ядра.

**Тревожные признаки**
- «Производительность и конфиг — потом».
- Логика захардкожена под один демо-сценарий.
- Нет разного поведения для разных потребителей.

### 3. Сила решения: чем лучше базовых инструментов / конкурентов?

Вопрос: *«Что есть такого, чего нет у других, и нужно ли это бизнесу?»*

**Хорошие признаки**
- Продвинутые фичи: матчинг со справочниками/БД, токенизация, синтетика, маскирование по **комбинациям** типов ПД, документы не только РФ, высокая нагрузка.
- Честно и ясно про ограничения / где подход может сломаться.
- У каждой фичи понятное бизнес-обоснование.

**Тревожные признаки**
- Фичи «для галочки» без цели.
- Не могут объяснить пользу для бизнеса.
- Звучит круто на словах, в демо не видно.

### Стратегия: выше ожиданий с первого дня

- **Целимся в дополнительные требования**, не только в минимум ТЗ.
- Архитектуру, конфиг, API и демо **сразу проектируем** так, чтобы бонусы (токенизация/синтетика, гибкие настройки по системам, комбинации ПД, RPS 2000, доп. документы и т.д.) были естественным продолжением, а не «прикрутить в конце».
- MVP нужен быстро, но **без тупиковых решений**, которые режут путь к доп. требованиям и оценке «впечатляет» (3/3 на защите).

Приоритет исполнения: рабочий happy path **на правильной архитектуре** → must-have (95%, SLA, `/process`, RU-сервер) → **доп. требования и wow для защиты**.

### Must-have для MVP

1. Proxy: consumer → identify/mask → LLM → unmask → response.  
   Языки: **RU обязательно**, EN желательно. Смысл промпта для модели сохраняется; мало ложных срабатываний (Пушкин / адрес банка ≠ ПД).

4. Метрики **Latency / RPS / TPS**; логи без сырых ПД; URL на **российском сервере** + `docker compose up` + README.  
5. Чистый **только `.zip`** с исходниками (без `node_modules`/`.venv`/`venv`/`.git`/`.env`/build).
