# Этап 3 — нагрузочное тестирование MVP v1

Дата: 2026-09-23  
Публичный сервер: http://135.106.220.67  
Endpoint: `POST /process`

## Проверка доступности

- `/ready` → HTTP 200, `{"status":"ready"}`
- `/health` → HTTP 200
- storage: `redis`
- systems: 5
- pd_types: 20
- `/process` успешно маскирует тестовый запрос
- HTTPS на IP: не поднят; тест выполнялся по HTTP

## Методика

Использован существующий `scripts/load_smoke.py`.

Основной SLA измеряем в `mode=create`: один запрос = один HTTP POST на `/process`.

Нагрузка увеличивалась ступенчато:
- concurrency 20
- concurrency 50
- concurrency 100
- concurrency 180

Дополнительно:
- полный цикл `mask → demask` при concurrency 50;
- текст около 100 000 токенов по принятой в скрипте эвристике `chars/4`, concurrency 2.

Это предварительный ramp-test. Официальный прогон организаторов длится около 5 минут при целевых 1000 RPS. Поскольку текущая сборка уже показала насыщение значительно ниже 1000 RPS, длительный 1000-RPS stress-run до оптимизации не запускался.

## Сопоставление с требованиями

### RPS ≥ 1000

**Не достигнуто.**

Лучший измеренный результат текущего ramp-test:
**582.8 RPS** при concurrency 100.

При увеличении concurrency до 180 throughput не растёт, а падает до 347.7 RPS, одновременно p95 растёт до 3.5 секунды. Это признак насыщения / очереди внутри текущей конфигурации.

### Latency ≤ 1 с

До точки насыщения требование выполняется:
при concurrency 100 **p95 = 284.3 ms**.

При concurrency 180 требование уже не выполняется:
**p95 = 3512.1 ms**.

Целевой ориентир жюри `p95 ≤ 500 ms` выполняется на concurrency 20/50/100, но перестаёт выполняться после насыщения.

### Текст до 100 000 токенов

Сервис не падает: **10/10 запросов успешны**.

Но обработка медленная:
- p50 = 3.50 с
- p95 = 7.04 с

То есть функциональная поддержка большого контекста есть, но latency общего SLA на таком размере не выполняется.

## Вывод

Текущий MVP v1 стабилен на умеренной нагрузке и не даёт HTTP-ошибок в проведённом ramp-test, но **не достигает целевых 1000 RPS**.

Наблюдаемая рабочая точка в этом прогоне — около **583 RPS при p95 284 ms**. После неё система входит в насыщение: увеличение параллельности ухудшает и throughput, и latency.

Перед повторным финальным нагрузочным тестом нужно оптимизировать узкое место, после чего повторить тот же набор прогонов и затем, если 1000 RPS достигнуты, провести официальный-style sustained test около 5 минут.
